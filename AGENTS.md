# AGENTS.md — trust-LiMe

TRUST-LiMe is a **baltik application**: a C++ module built on top of the CEA
[TRUST](https://github.com/cea-trust-platform) kernel. It adds a magnetic-field
convection–diffusion equation on top of the existing thermohydraulics, to model
coupled MHD. Kernel sources live in a sibling checkout (`../trust-code`); this
repository only contains the module.

## Repository layout

| Path | Purpose |
|---|---|
| `src/` | Module sources: `Pb_MHD.{h,cpp}`, `Convection_Diffusion_Magnetic_field.{h,cpp}` |
| `build/` | Generated by `./configure` (symlinks to `src/`, CMake files). Do not hand-edit. |
| `share/Validation/Rapports_automatiques/` | Validation notebooks + `jdd.data` cases |
| `docs/` | Doxygen documentation (TRUST/baltik pipeline). Build with `make docs`; see the `trust-lime-docs` skill. |
| `compile_commands.json` | Platform-wide compiler flags (from trust-code). Flags are valid, but the database is not module-aware. |
| `.opencode/` | Agent configuration: commands, skill, scripts (this harness) |

## Build (baltik)

Always run from the repository root. The TRUST kernel must already be built.

| Command | Meaning |
|---|---|
| `make module_semi_optim` | **Default.** Rebuilds only this module, `-O3`, asserts on. Fast path. |
| `make module_optim` | Module, optimized. |
| `make module_debug` | Module, debug symbols / asserts (for gdb, valgrind). |
| `make optim` | Full build: kernel + module. Slow. |
| `make semi_optim` / `make debug` | Full build in that mode. |
| `make module_custom` | Module with `project.cfg` `cpp_flags`/`ld_flags` (see sanitizers below). |
| `make check_optim` / `make ctest_optim` | Baltik / ctest test suites (also `_semi_optim`, `_debug`). |
| `make help` | List every target. |

## Getting diagnostics fast

OpenCode V2 supports LSP, but it is deliberately disabled for this repo (see
`opencode.jsonc`): clangd would index the full TRUST kernel
(`compile_commands.json` is ~25 MB), which is not worth the cost on either dev
host. The fast path is the compiler directly; use it instead of waiting for a
full build:

```bash
bash .opencode/scripts/syntax-check.sh src/Pb_MHD.cpp
```

`/syntax <file>` wraps this. It reuses the real flags from
`compile_commands.json`, runs `g++ -fsyntax-only`, and finishes in seconds. Use
it after every meaningful edit, before a `/build`.

Two extra switches are available:
- `EXTRA_CXXFLAGS="-I/path"` appends flags (needed for the GoogleTest headers).
- `SYNTAX_CHECK_PRINT_FLAGS=1` prints the flags instead of compiling — this is
  how `unit-tests.sh` reuses exactly the same flags.

> **The recorded `compile_commands.json` is stale**: it says `-std=c++17`, but the
> kernel is really built with **`-std=c++20`** (see `trust-code/compile_TRUST_*_opt_*.log`),
> and the bundled Kokkos headers fail to parse under C++17. `syntax-check.sh`
> therefore forces `-std=c++20`. Keep that override if you touch the script.

## Validation (Jupyter)

Notebooks live under `share/Validation/Rapports_automatiques/` and must run
inside the **TRUST Python environment** (`venv_trust` + TRUST env), not the
OpenCode venv. One validation form per test case, at
`<Category>/<FormName>/<FormName>.ipynb`; current forms: `MagneticStandalone/*/`
(2D) and `MagneticStandalone3D/*/` (the 3D twins — same form names; 3D
datasets add `Polyedriser dom` after `Mailler`, PolyMAC_MPFA needs polyhedra
in 3D). Example: `MagneticStandalone/Diffusion/Diffusion.ipynb`. Use
`/validate`.

**Formatting rules — enforced by `.opencode/scripts/check-validation.sh`
(`/check-validation`):** the `.ipynb` lives at the form root only
(`Rapports_automatiques/<Category>/<FormName>/<FormName>.ipynb`, never in
`src/`), each notebook runs **one and only one test case** (one `addCase`),
and **all cases run sequentially** — `.data` files must never contain TRUST
parallelism machinery (`Decouper`/`Partitionneur`/`Scatter`/`Larg_joint`/
`Nom_Zones`/…), and notebooks must not call `partition()` or set `nbProcs>1`.
**Parallel exception.** A form may run on `N` cores only if its path is listed in
`parallel_ok[]` in `check-validation.sh`. The dataset must then carry the three
comment-marker regions (`# BEGIN MESH #`, `# BEGIN PARTITION`, `# BEGIN SCATTER`)
that `trust -partition` toggles. Currently the allowlisted forms are:
MagneticStandalone/Invariance/ (2D + 3D), MagneticStandalone/Diffusion/,

## Known gaps / open items

- **`ForceLorentzBalance`** (MagneticCoupled): runs sequentially pending a parallel-safe pressure solver. The kernel's SSOR preconditioner does not support the Matrice_Morse type used by the coupled system; PETSc `hypre` alternative converges the magnetic solve but the Navier–Stokes solve later diverges (`KSP_DIVERGED_NANORINF`). Decision needed: keep sequential or debug the parallel divergence (lagged `b` Lorentz source / aux-element velocity dofs under partitioning).
- **`MMS_Poly_2D`**: dataset only, no notebook, non-standard `# PARALLEL OK 1 #` header, unused near-duplicate of `MMS_Trig2D`. Delete or complete as a form.
- **`MMS_Diff3D`**: ported, allowlisted `.data` but no notebook; 2D/3D twin rule (R5) is broken — add the 3D notebook or drop from allowlist.
- **`Stretching`**: legacy reference run with assertion-free notebook, allowlisted and marked but excluded from the PDF runner. `SourceStretching` is the validated replacement.
- **MMS/Stretching notebooks**: three MMS notebooks + `Stretching` have no `assert` in their source; they are smoke/convergence data producers, not validation forms as advertised.
- **`force_lorentz` coupling is one-way**: the NS velocity does not feed the magnetic convection; low-Rm limit (Rm ≪ 1) validated against Tassone et al. breeding blanket parameter ranges.

## Compiler & style constraints

- **C++20**, `-mavx`, `-O3`, `-Werror` with `-Wall -Wextra -Wconversion -Wshadow
  -Woverloaded-virtual -Wnon-virtual-dtor -pedantic`. **Warnings are errors** —
  keep them at zero. `-Wconversion` is the usual trap (implicit `double`→`int`,
  sign mismatch).
- Kernel headers are included **with** the `.h` extension:
  `#include <Convection_Diffusion_Temperature.h>`.
- A `.clang-format` is provided, but automatic formatting on write is **off**
  (see `opencode.jsonc`); turn it on deliberately.

Full idioms (`Declare_instanciable`, `Param`, `REF(...)`, Doxygen mandates,
`// XD` tags, the class-extension recipe): **`trust-lime-coding` skill**.

## Extending the kernel from trust-LiMe

Reuse kernel base classes (e.g. subclass `Convection_Diffusion_Temperature`)
rather than reimplementing; see the recipe in the `trust-lime-coding` skill.
Kernel sources are available as the `trust-kernel` / `trust-include` references.

**`KERNEL_REUSE_NOTES.md` (repository root) is the accumulated knowledge base**:
kernel class choices, keyword-reading order, CL compatibility rules, the
`Champ_Inc_base` requirement for the transporting velocity, field factories, and
pointers to the exact kernel sources. Read it before extending the module, and
append new findings there.

## Current state

- `src/Convection_Diffusion_Magnetic_field.{h,cpp}` and `src/Pb_MHD.{h,cpp}`
  have been **rewritten from scratch**. Both pass `syntax-check.sh`.
  The historical defects (self-including `Pb_MHD.cpp`, mismatched
  `equation(int)` overloads, missing `.h` in kernel includes, missing `;`/`};`)
  are **fixed**.
- The module solves the **standalone** magnetic induction equation
  (see `docs/content/model.md` and `PLAN_magnetic_standalone.md`).
- Validation cases: `share/Validation/Rapports_automatiques/MagneticStandalone/`
  (2D) and `MagneticStandalone3D/` (the 3D twins, same form names) —
  self-contained `Mailler`/`Pave` meshes (3D uses `Polyedriser dom`),
  analytic + invariant checks. See `docs/content/test_cases.md`.
- Kernel and module **are built** (`trust-lime`, `trust-lime_semi_opt`,
  `trust-lime_opt` exist at the repo root) — the historical `libparaconf`
  configure blocker is resolved.
- **All 22 MagneticStandalone validation notebooks pass in 2D and 3D**
  (checked 2026-10-15; `Hartmann1D` added last) and are concatenated into a
  single `MagneticStandalone_validation.pdf` at the repo root by
  `.opencode/scripts/run-validation-pdf.sh` (rc=0). Multi-component
  `nb_composantes` works and is exercised by the post-treatment forms
  (`vecteur_poynting`, `helicite_croisee`) and by `Hartmann1D`
  (`nb_composantes 2`); the old `VectorComponents` form remains removed.
- **Post-treatment fields** (cyclotron pulsation, magnetic energy, Poynting
  vector, crossed/kinetic helicity, magnetic Reynolds and Prandtl numbers,
  magnetic tension) are exposed by the equation via
  `creer_champ`/`has_champ`/`get_champ` with a field class
  `src/Champ_Fonc_MHD.{h,cpp}` — validation forms live in
  `share/Validation/Rapports_automatiques/Postraitement_fields/<FormName>/`
  (one form per field). The recipe lives in `KERNEL_REUSE_NOTES.md` §11.
- The `induction_stretching` source needs the velocity face field's
  **auxiliary element variables** or `grad_u` reads garbage — see
  `KERNEL_REUSE_NOTES.md` ("Getting a velocity gradient for free"). Its element
  gradient is also **biased in the two cells adjacent to a wall** (the kernel
  averages face gradients and a boundary face only gets a Dirichlet
  contribution; measured exactly halved for a linear velocity). `Hartmann1D`
  documents and bounds that effect — see `KERNEL_REUSE_NOTES.md`.
- **Divergence of the magnetic field** `∇·b`: the module assumes `∇·b = 0`
  but does **not enforce** it (same pattern as the thermalhydraulics velocity
  field). The `∇b` is reconstructed via Green–Gauss (`gradient_b_elements`)
  — this reconstruction is **exact for linear fields at interior cells** (all
  faces have neighbours). Boundary cells (walls with homogeneous Neumann CLs)
  have O(h) accuracy due to the "zero normal gradient" approximation (`bf =
  b(e0)` at walls). **Validation probes must target interior cells** when
  comparing against an analytic field.  A lightweight divergence-correc-
  tion at interior cells can be added post-hoc (see Path 2 below), but the
  raw Green-Gauss value is already correct for the intended validation use
  case.  Path 2 (pressure-correction approach, detailed below) would achieve
  machine‑precision ∇·b = 0 globally but requires new solver infrastructure
  beyond the M0/M1 standalone scope.
- **Coupled low-Rm mode (Lorentz force) is wired**: `Pb_MHD` accepts optional
  extra equations (kernel `eq_opt_` mechanism) — adding
  `Navier_Stokes_standard` to the problem block gives a two-equation coupled
  problem, and the `force_lorentz` source (`src/Terme_Source_Lorentz.{h,cpp}`,
  J×B per unit mass, lagged b, Boussinesq-PolyMAC face/element assembly)
  couples b → momentum. One-way only: the NS velocity does not feed the
  magnetic convection yet. Validation form:
  `share/Validation/Rapports_automatiques/MagneticCoupled/ForceLorentzBalance/`
  (Lorentz hydrostatic balance: Δp = −0.1886 vs analytic −0.18, |u| → 0).
  Recipe and traps (source-typing suffix, `solveur_pression`, the static
  `trust-lime_opt` rebuild) in `KERNEL_REUSE_NOTES.md` §12bis.
- **Unit tests** live in `tests/UnitTests/` (GoogleTest, kernel conventions).
  The arithmetic suite (`--arith-only`) **runs and passes** today; the rest
  needs the full kernel.

## Sanitizers (local debugging)

`project.cfg` exposes `cpp_flags` / `ld_flags` (currently commented out). For a
local ASan/UBSan build, set:

```ini
cpp_flags : -fsanitize=address,undefined -fno-omit-frame-pointer -O1 -g -Wno-error
ld_flags  : -fsanitize=address,undefined
```

then `./configure && make module_custom`. Revert `project.cfg` before normal
builds. See the `trust-lime-coding` skill.

## Data file comment convention

- Comments in `.data` files must use the `# ... #` format: a `#` at the
  beginning and a `#` at the end of the line, with spaces between the `#`
  markers and the comment content (e.g. `# this is a comment #`).
  Alternatively, C-style `/* ... */` block comments are accepted.
- This rule ensures consistent parsing since TRUST data files have no line
  concept and use block-based syntax.
- The earlier `# bla #` style is formalized here and can be removed from
  "To sort" once confirmed.
